# Reopen design system

## Direction

A warm editorial decision notebook for operating work. The first view makes a decision’s original reason tangible, with later evidence in the margin. Burgundies, warm ivory paper and restrained tan structure distinguish Reopen from the other portfolio applications. The source transcript and checklist consequence are the visual proof; decorative charts and generated hero art have no role.

The user’s existing code-first preference and approved notebook direction override concept-image approval workflows. Impeccable was loaded for new work and the craft floor. Its direction seed was run; the pinned editorial notebook identity remains authoritative.

- Body text13–16px; prominent evidence26–28px; desktop heading44–67px.
- Thin ruled divisions; controls have5px radii. No repeated dashboard card scaffolding.

## Layout and interaction

Desktop uses a232px private notebook sidebar, generous reading column and278px evidence margin. The journal preserves original rationale, then assumptions and review condition, then source quotation and checklist anchor. Evidence view pairs a selectable source list with focused comparison and explicit action controls. Editors are pages within the notebook, not modals.

Mobile uses a sticky header and an explicit navigation toggle. Panels stack in reading order. Data never requires horizontal scrolling. The evidence margin is omitted when narrow because the full Evidence destination remains available. Forms use full-width controls with16px text on mobile.

Changing views keeps task continuity. Save buttons disable during mutations and show status. Toasts arrive once from an already visible default; reduced-motion disables animation. Focus rings, caret, text selection, scrollbar and native inputs use the same palette. Actual request errors stay visible and explain recovery.

## Product truth

Manual imports are always manual. All illustrative source material is marked fictional. Bee/AWS disconnected status is visible. Review suggestions are not verified facts. A reopened decision cannot change a checklist until a concrete replacement is previewed and approved separately.

## Decision history interaction — 8 September 2026

The focal moment is moving between actual saved decision versions. A horizontal version rail synchronizes the recorded rationale, assumptions, source, reviews and approved checklist consequences. Keyboard Left/Right and Home/End select recorded positions; absent version numbers are not invented. Exact field comparisons show previous and selected values without claiming causal links from textual similarity.

The reader uses one cancellable 180 ms opacity/clip transition when selection changes, never on initial load. New content exists immediately. Reduced motion removes the reader animation while the selected tab retains fast color feedback. No canvas, continuous animation, 3D scene or added motion dependency is needed for this reading workflow.

Evidence snapshots remain immutable and outrank current wording when reading old versions. A partial historical record explicitly says its wording was not saved. Sources are shown through stored source IDs; checklist consequences are shown only through saved evidence/proposal references. Selecting paired evidence and returning to history keeps that review’s original decision version selected.


## Bee source connection — 12 September 2026

Sources now contains an explicit connection and selection surface using the existing paper, wine, serif heading and restrained borders. The sequence explains what each action reads: permission for metadata, selection of at most five conversations, then permission to store transcripts and processed context. A persistent connection badge and last-checked/error state distinguish saved authorization from successful retrieval. Fixture transport is visibly labeled.

The source list retains immutable revisions, retrieval origin, reported device type and processed context. A Bee-sourced draft places context beside the original quote and requires an explicit wording check before confirmation. The server enforces that check. Selection backgrounds respond immediately, buttons show pending work, and reduced motion disables the short color transition. Mobile stacks the connection header and keeps actions full width. The notebook’s decision/review/checklist authorization sequence remains unchanged.

Observed implementation friction: local sandbox policy initially prevented disposable HTTP test listeners; the suite ran successfully once loopback execution was permitted. No user interview or device feedback was conducted. Browser observations are recorded separately with the actual verification artifacts.


The final fixture browser walkthrough passed on desktop and at 390px width, including keyboard wording confirmation, reduced motion, selected imports, paired review, checklist approval and disconnect/reload. A delayed-response regression holds actual successful HTTP import responses during notebook and account changes; old receipts and source content never replace the new view. The connection remounts for a changed session/notebook/navigation generation and keeps response feedback local to its initiating view. The inspected screenshots remain readable with no horizontal overflow. This validation uses fixtures and is not user or device feedback.

## Assistant decision review — October 2026

The Assistant surface follows the same paper-and-wine notebook design. Connection consent names the notebook and exact permission. Read-only is the default; a draft permission never grants approval. Real protocol operations and returned decision/evidence data form the demonstration, without a fabricated chat transcript or an Alexa device claim. Tokens remain transient, hidden from persistent storage and separated from shareable evidence. Account and notebook switches clear the client connection.
